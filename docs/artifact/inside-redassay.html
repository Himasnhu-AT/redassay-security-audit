redassay — a security audit loop for Claude Code

A scanner that stops before it edits your code

Point a language model at a repository and ask for the security bugs and you get a wall of markdown: unreviewable, unrepeatable, and impossible to say no to permanently. redassay splits that into three pieces that talk through files on disk — and puts a human between finding something and changing anything.

It answers three questions, not one

Different mechanisms — none can substitute for another

Most scanners answer only the first. The other two decide whether the first one's answers matter, which is why a tool that only does pattern matching produces a backlog rather than a plan.

The scan pipeline

Deterministic end to end — same input, same output, no model, no network

01

Walk walker.py

Honours .gitignore and .redassayignore, sniffs binaries, caps file size, yields in a deterministic order so two runs cannot disagree.

02

Prefilter prefilter.py

Extracts the literal a regex must match, then asks one cheap question of the whole file before matching a rule line by line. Covers 96% of the rule set and measures 2.3–3× faster, with output verified byte-identical.

03

Scan scanners/

Eleven scanners run over the same file list. One raising an exception does not stop the others — a scan that dies on a malformed file in a repository you are auditing for the first time is useless.

04

Triage triage.py

Deduplicates by concept rather than rule id, so two scanners reporting the same line collapse to the better-evidenced one. Then ranks by severity weighted by confidence.

05

Merge store.py

Folds the result into what is already there: refreshes where a finding is, never touches what a human said about it. A fix that reappears reopens with a comment; one that stays gone becomes verified.

Why a finding's id excludes its line number

The single decision the whole store rests on

id = sha256(rule_id | path | normalized_snippet)[:12]

Code moves. The vulnerability does not. Add twenty lines above a finding and a dismissal somebody made last month must not come back — so the line number is deliberately not in the hash.

normalized_snippet collapses whitespace and blanks the contents of string literals. A hardcoded password rotating from hunter2 to hunter3 is the same finding, and the secret itself never feeds the hash — which matters because ids end up in logs and CI output.

The trade-off Two structurally identical findings on different lines of the same file collide. The scanners break that tie with a salt on repeat matches. Every identity scheme trades something; this one trades collision resistance for surviving a refactor, because the second is what a reviewer's time is spent on.

Reachability, and what it refuses to claim

Severity says how bad; nothing else says whether anyone can get there

Two findings, same rule, same severity, same file. One is called by an unauthenticated POST; the other is called by nothing: 

! high  py.shell-dynamic  app/db.py:7
    reachable from POST /report in 1 hop(s): report -> run_report

. high  py.shell-dynamic  app/db.py:12
    no call path from any known entry point

redassay does not build the call graph. A real interprocedural analysis needs one, and a wrong answer from a half-built graph is worse than no answer — it produces confident nonsense, which is the failure mode that gets tools uninstalled. So callgraph.py is a bridge: it shells out to an external indexer, reads its edges, and goes quiet when there is none.

. never renders as “unreachable”. A static call graph cannot see dynamic dispatch, reflection, framework registration, or anything wired at runtime. The status is a statement about the graph, and the output says so every single time it appears.

The review loop

The board never edits code — it appends to a queue

The engine and the agent

  • Scan, map the surface, rank by reachability
  • Add what rules structurally cannot find — authorization gaps, logic flaws, unsafe data flow
  • Confirm or dismiss its own low-confidence findings, with reasons
  • Drain the approval queue, patch, record the diff
  • Rescan to verify — or report that a fix did not clear it

You

  • Read a ranked list, not a wall of markdown
  • Approve a fix, with a note about what it must preserve
  • Dismiss with a reason that survives every future scan
  • Comment for whoever reads this file next
  • Select several and approve them together
Nothing edits code until you approve a specific finding. The thing you click and the thing that writes to disk are separate processes, and the second only ever acts on what the first recorded. That separation is the point of the design, not an implementation detail.

Limits that are decisions

Written down so you can judge whether the tool fits

The engine imports nothing outside the standard library

Enforced in CI. A security tool gets pointed at code you do not trust yet, often on a machine you do not control, frequently with no network. Requiring pip install — and with it a transitive dependency tree you have not reviewed — undercuts the thing it is for.

The cost is real and paid openly: no YAML parser, no tree-sitter, no HTTP client. The JavaScript analysis is regex over a normalized view rather than a parse tree, the YAML reader tracks indentation and nothing else, and the advisory database is an offline snapshot you refresh deliberately.

Confidence is a separate axis from severity

critical high medium low

Severity is impact if the finding is real. Confidence is how sure the rule is that it is. The board ranks by the two multiplied, so a speculative critical sits below a verified high. Inflating confidence is how a tool teaches people to skim past its output — and then the real criticals go unread too.

Three known misses

  • —Taint does not cross function boundaries without an external call graph. A helper taking a tainted argument is not connected to its caller.
  • —The dependency data is a snapshot. It goes stale. Pair it with a live feed for dependency coverage specifically.
  • —Authorization correctness cannot be decided by a scanner at all — which is precisely why the model-driven half of the audit exists.

What it actually does

Reproducible with tools/evaluate.py and tools/benchmark.py

On deliberately vulnerable applications

Every critical was opened and read. On a Django training app: SQL injection via string concatenation, command injection through a shell subprocess, eval() on a request parameter, path traversal, SSRF, pickle deserialization — all found, each with the taint source named in the description rather than left for the reader to re-derive.

On a large framework

Everything7010.72
Excluding tests202 at high+0.36

59% of the findings came from the project's own test suite — files that construct malicious input on purpose. Most of the rest are in the ORM's schema backends and the templating helpers: a framework implements SQL construction and HTML escaping, which are exactly the primitives the rules look for.

The honest conclusion is that redassay is tuned for application code, not framework internals. On an application that uses a framework, the same rules fire almost exclusively on real problems.

The false-positive budget, written as a test

fixtures/clean-app/ is idiomatic, safe code — the correct form of everything the rules flag elsewhere. It produces exactly one finding: a low-confidence note on an allowlisted fetch, where the taint tracker can see a guard but cannot verify it is strict enough. The suite asserts it never produces a high-confidence finding.

Rules test themselves Every rule carries an example it must match and a counterexample it must not, run against the scanner by the test suite. Adding that mechanism found seven silently broken rules — including five whose literal matcher could never match a quote inside a differently-quoted string, so the most-used SQL rule was missing WHERE name = '" entirely.
